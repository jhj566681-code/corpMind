## 1. 实施约束

先后端、后前端；使用虚构业务数据，模型接口与模拟接口分离。需求、设计、测试和实现保持一致，不提前把计划标为完成。

文件修改范围以当前用户任务为准，保留无关修改。本文中的代码目录、依赖、CI和部署配置均为里程碑计划，不代表已实现，也不构成额外文件操作或提交、推送、合并的授权。

## 3. 任务管理与版本控制

每个工作项记录：关联FR或AC、目标、输入输出、实施范围、验证方法、完成条件。缺陷记录预期、实际、复现条件、影响和修复验证。

日常流程：更新main → 创建codex/主题分支 → 小范围实现 → 本地验证 → 查看差异 → 提交和推送 → Pull Request审查 → 合并。已有未提交修改先审查并明确归属，不覆盖或强行重置。

GitHub Desktop用于分支、差异和提交；VS Code用于实现与调试；GitHub用于工作项、PR和CI。三个工具均针对同一个corpMind目录。AI辅助审查不能代替开发者理解和测试。

提交信息使用docs、feat、fix、test、refactor或chore前缀，内容描述具体行为。一个PR只解决一个可独立验收的任务。单人项目由开发者自审差异，记录AI辅助意见的核对结果，不伪称独立人工审核。

## 4. 实现边界与工程规则

- 使用项目独立虚拟环境；依赖按实际验证结果锁定，记录Python和模型配置。
- API、Agent、工具、检索、存储、业务规则分层；所有访问和写入最终经过业务服务。
- 外部模型和业务接口使用适配器；测试默认模拟，不调用付费服务或真实平台。
- 未来项目结构分为后端、界面、测试、模拟资料、配置与迁移；具体代码布局在M1验证后定稿。
- 业务规则、契约、状态机及权限均可独立测试。程序不读取任意本地文件，不执行模型生成的代码。
- 配置由环境读取；版本库只提供不含秘密的配置示例，用户数据与本地运行产物不入库。
- 正常日志记录请求ID、任务ID、工具名、状态、耗时和错误代码；敏感字段脱敏。
- 修改模型、提示词、资料、检索参数或工具定义时，同步记录版本并重跑受影响的测试与评测。

## 5. 质量检查与完成定义

功能完成需要：需求已明确、实现已审查、正常与失败测试通过、文档同步、变更范围清楚、能够解释与复现。计划、部分实现和已验证分别记录。

CI从建立可执行项目后接入，默认执行Ruff、单元测试和本地模拟集成测试；不得依赖开发者机器上的文件路径、密钥和付费API。重要行为测试包括权限、确认、幂等、失败恢复和引用校验。

数据库变更提供前后版本及迁移验证。合并前确认目标分支、实际差异和所有必需检查；不跳过失败检查并把任务标为完成。
