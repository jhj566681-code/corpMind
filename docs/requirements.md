# corpMind 需求规格

版本：v0.2。日期：2026-10-26。状态：G0 需求基线已评审；全部功能尚未实现。确认依据见 [G0 评审记录](g0-review.md)。

## 1. 目标与边界

帮助客服调查售后异常，基于政策和实时查询事实形成处理方案，经人工确认后创建本地售后工单。项目同时验证 RAG、动态工具选择、任务状态及软件工程交付能力。

首版：一个虚构企业、两个业务组、签收未收到和运输延迟两类任务。本地模拟订单、物流、政策与历史案例。处理方案是调查建议，不是退款结论或审批承诺。

不包含：真实退款、客户消息发送、真实平台接入、多租户、任意代码执行、开放网页爬取、复杂多 Agent、模型训练及扫描图片识别。

## 2. 用户与权限

| 用户 | 权限 |
| --- | --- |
| 客服A | 调查业务组A订单，查看通用和组A知识，访问本人创建的任务与工单 |
| 客服B | 调查业务组B订单，查看通用和组B知识，访问本人创建的任务与工单 |
| 知识管理员 | 维护知识与授权范围；不因管理员角色自动获得全部订单或他人工单权限 |

身份和业务组取自后端登录会话。工具参数和聊天内容不能覆盖身份。访问检查适用于检索、原文、任务、工单、历史案例及 MCP 服务。未授权对象统一返回不可用信息，不泄露其正文、标题或是否存在。

有效凭证可登录，错误凭证返回统一认证失败；注销后原会话不能继续访问受保护资源。同组客服也不能访问他人创建的任务、工单、笔记或事件。知识管理员的资料管理能力不扩大其业务数据权限。

## 3. 用户故事与主流程

- US-001：作为客服，我希望核查签收未收到的订单，以便给出有证据的处理方案。
- US-002：作为客服，我希望核查运输延迟，以便判断是否应创建延迟调查工单。
- US-003：作为客服，我希望确认方案后只创建一次工单，并能恢复失败任务。
- US-004：作为知识管理员，我希望维护有效政策和可见范围，使客服使用适用资料。

主流程：输入问题 → 明确本次调查的唯一订单 → 查询订单与物流 → 检索适用政策与必要历史案例 → 汇总证据与缺口 → 展示方案 → 客服点击“确认创建” → 创建本地工单 → 展示真实执行结果。

“缺少订单号”“需要核验代收情况”“工具失败”“无权限”分别处理，不强行走完固定步骤。

客户反馈已找回包裹，或关键证据齐全且运输尚未达到延迟调查门槛时，展示当前结果并完成本次调查，工单为0条；以后需要查询时重新发起任务。

## 4. 虚构业务规则

以下规则仅用于教学与测试，不能代表真实商家政策。

| 编号 | 规则 |
| --- | --- |
| BR-001 | 单任务只调查一个明确订单；缺少订单号时保留任务并追问，多个候选订单时先请客服选择，再查询；不能按姓名猜测订单或查询无关对象 |
| BR-002 | 签收状态不等于客户本人收到。存在代收且客户未核实时，询问核验情况并等待补充；客服补充“已核实仍未找到”后，保留为客户陈述，其他关键证据齐全且无冲突时可形成签收异常调查方案，不认定已经丢件；若客户反馈已找回并拿到包裹，展示该陈述并完成任务，零工单 |
| BR-003 | 运输中且当前时间严格晚于预计送达时间48小时（超时时长>48小时），关键证据充分且无冲突时可提出延迟调查方案，经人工确认后创建工单；当前时间取自查询服务，不由模型猜测；证据缺失或冲突时遵循BR-005 |
| BR-004 | 当前时间不晚于预计送达时间时，展示当前轨迹与预计时间，不认定延迟；运输中已超时但不超过48小时（0<超时时长≤48小时，含恰好48小时）时，说明实际延迟和尚未达到调查门槛。关键证据齐全且无冲突时，上述两类情况均不提出延迟调查工单方案，展示结果后完成本次调查，零工单；后续查询需重新发起任务；不能编造延误或保证送达，证据不足或冲突时遵循BR-005 |
| BR-005 | 订单、物流和政策任一关键证据缺失或冲突时，列出已知事实及缺口，暂停确定性处理结论 |
| BR-006 | 工单记录调查请求，不执行退款、补发、物流变更或对外通知 |
| BR-007 | 创建工单需要当前登录客服点击“确认创建”，绑定其本人任务的当前版本方案；普通聊天、补充核实结果、取消和否定不构成确认。暂缓时保留待确认方案；否定方案时旧方案立即不可确认，追问原因并修订，新方案重新确认；明确取消调查时结束任务。上述未确认分支均不创建工单 |
| BR-008 | 同一任务同一方案重复确认只返回同一工单；未成功创建前，方案变化或关键业务记录更新使旧确认失效，确认前重新核验权限与证据；已成功创建的同一方案在重复确认时，经身份、业务组权限和资源归属检查后返回已有工单，不再次执行写入，也不因后续记录变化再建工单 |

## 6. 非功能要求

- NFR-001 权限与写入：固定权限测试零泄露；未经确认、重复创建及跨用户访问属于阻断发布的问题。
- NFR-002 执行边界：每次运行最多6次模型请求、8次工具尝试、60秒活动执行时间；只读瞬时故障最多重试1次，计入上限；整个任务累计最多32次工具尝试。等待用户输入不计入活动时间。
- NFR-003 状态一致性：创建工单与记录执行结果使用数据库事务，进程中断后不得出现重复工单。
- NFR-004 可复现：测试使用固定时钟、固定业务记录和受控故障。正式评测记录资料、模型、提示词及代码版本。
- NFR-005 成本：初始模型试验预算100元。记录用量和已知单价估算；未知费用不得记作零，供应商账单为实际费用依据。
- NFR-006 可维护：模型、检索、工具和业务规则使用独立接口；业务判定可被独立测试。
- NFR-007 交互：界面展示任务阶段、工具执行摘要、来源与失败信息，不声称未发生的业务动作已成功。

模型服务耗时与费用在技术验证后实测。上述时间是停止边界，不是响应速度承诺。

## 7. 数据与结果要求

- 政策必须有文档ID、版本、适用范围、可见范围和原文位置；只检索适用且有效的版本。
- 相同规范化内容在相同授权范围内重复导入时，返回已有记录，不新增副本；导入操作不能隐式扩大既有资料权限。
- 客户陈述保留消息来源，并与工具查询到的事实分开。客户表示未收到不等于系统已证实丢件。
- 订单、物流证据保留记录ID、版本和查询时间。历史案例是参考，不覆盖当前政策或事实。
- 处理方案保留订单号、问题类型、事实、政策依据、缺口、建议动作、证据列表及方案版本。
- 模型提出的事实或字段缺少来源时，不能作为确定结论或写入依据。
- 更新或删除政策后，新请求不能检索旧版本；已有引用标记过期或删除，确认前重新核验。
- 历史案例只使用管理员维护的虚构案例；失败任务和用户反馈不自动进入“成功经验”。

## 8. 验收与变更

本版已由用户确认首版范围、FR、BR、NFR、角色及验收目标，G0 需求评审通过，详情见 [G0 评审记录](g0-review.md)。详细场景和通过标准见 [测试计划](test-plan.md)；验收设计尚未执行，不存在应用测试、模型评测或部署通过的结果。

新增工具、权限、业务分支或数据来源时，记录需求编号、接口与数据影响、用例变化、成本和工期影响，再更新需求及设计。真实平台接入、退款能力和多 Agent 作为独立变更评审。
